# Plan: Fase 3 — login

**Tanggal:** 2026-11-10
**Status:** ✅ Selesai 2026-11-16, kecuali 6b (user mencoba login) dan 6c (brainstorm Fase 4). Disetujui 2026-11-10, lalu dikerjakan satu langkah per hari, 10–16 Nov.

## Tujuan

Dashboard hanya bisa dibuka setelah login dengan akun sungguhan, dan halaman admin hanya untuk admin. Halaman publik tetap static dan tidak berubah.

## Keputusan user (brainstorm 2026-11-10)

| Hal | Keputusan |
|-----|-----------|
| Hash password | **scrypt bawaan Node** (`node:crypto`), tanpa paket tambahan. Format hash dicek ketat, jadi nilai yang bukan hash (seperti `!no-login` dari seed) selalu ditolak |
| Sesi | **Cookie httpOnly bertanda tangan**, ditambah cek user di database pada setiap request, sehingga akun yang dinonaktifkan langsung tertolak. Tanpa tabel baru |
| Lama sesi | **7 hari** |
| Akun contoh | **Satu password dev acak di `.env.local`**, tidak lewat chat dan tidak di-commit. Seed memakainya untuk semua akun contoh; E2E membacanya dari sana |

## Hasil: cara kerja login sekarang

**Password** (`lib/auth/password.ts`):

- scrypt N=32768, r=8, p=1, garam 16 byte, kunci 64 byte, format `scrypt$32768$8$1$<garam>$<hash>`.
- `verifyPassword` hanya menerima format dan parameter itu persis (parameter dibandingkan sebagai teks, base64url harus kanonik). Nilai lain tetap menjalankan scrypt sekali dengan garam dummy, supaya waktunya sama.
- Password berisi surrogate tunggal ditolak; perbandingan dengan `timingSafeEqual`.

**Password dev dan akun:**

- `npm run db:seed` (lokal) membuat `DEV_PASSWORD` dan `SESSION_SECRET` acak di `.env.local` kalau belum ada, tanpa dicetak. Semua akun contoh memakai `DEV_PASSWORD`, masing-masing dengan garam sendiri.
- Dengan `--remote` (juga lewat tunnel `localhost`), akun contoh tetap `!no-login`.
- `npm run db:set-password <email>`: password diketik dua kali dan tersembunyi, 8–1024 karakter; email dicocokkan tanpa membedakan huruf besar/kecil dan ditolak kalau lebih dari satu akun cocok.

**Sesi** (`lib/auth/session-token.ts`, `lib/auth/session.ts`):

- HMAC-SHA256 bawaan `node:crypto`, bukan `jose`: tanpa paket tambahan, dan cookie ini hanya dibaca server kita sendiri.
- Token `<userId>.<expiresAt>.<stamp>.<signature>` dengan tepat satu ejaan per sesi. `stamp` = HMAC dari `password_hash`, jadi mengganti password langsung mengakhiri sesi lama.
- Cookie `side_notes_session`: `httpOnly`, `sameSite=lax`, `path=/`, 7 hari, `secure` di produksi, dibuat baru setiap login.
- `SESSION_SECRET` kosong atau kurang dari 32 byte membuat app berhenti dengan error, tanpa nilai cadangan.
- `readSession` memanggil `io()` sebelum cek kedaluwarsa, supaya jam hanya dibaca pada request sungguhan.

**Siapa yang login** (`lib/auth/current-user.ts`, `lib/data/auth.ts`):

- `getCurrentUser()` memeriksa secret, cookie, akun di database (tanpa cache), `is_active`, lalu stamp. Role dan status aktif selalu dari database. `cache()` dari React hanya berbagi hasil dalam satu request.
- `requireUser()` mengalihkan tamu ke `/login`; `requireAdmin()` mengalihkan author ke `/dashboard`.

**Login dan logout** (`lib/auth/actions.ts`, `lib/auth/login-rules.ts`, `components/dashboard/login-form.tsx`):

- Server Action `login` lewat `useActionState`: field dicek `typeof === "string"`, email paling panjang 254 dan password 1024 karakter.
- Email tak dikenal dan akun nonaktif tetap menjalankan scrypt, lalu semua kegagalan mendapat satu pesan: "That email and password do not match an active account."
- Berhasil: cookie baru, lalu admin ke `/dashboard/review` dan author ke `/dashboard`.
- Form tetap jalan tanpa JavaScript; setelah gagal, email tetap terisi dan fokus pindah ke password.
- Log out adalah tombol `<form action={logout}>` (POST) di sidebar dan bar atas.

**Dashboard terkunci:**

- `proxy.ts` (`/dashboard`, `/dashboard/*`): tanpa cookie, atau dengan cookie yang palsu atau kedaluwarsa, mendapat 307 asli ke `/login`, dan cookie rusak dihapus. Tanpa database.
- Layout dashboard dan **setiap** halaman memanggil `requireUser()`/`requireAdmin()`, termasuk `generateMetadata` di halaman `[id]`, karena layout tidak dirender ulang saat berpindah halaman.
- Editor artikel hanya terbuka untuk penulisnya atau admin; artikel orang lain → halaman tidak ditemukan.
- Dashboard dirender per request (`instant = false`, tanpa `generateStaticParams`), jadi email penulis tidak lagi ada di HTML statis. Halaman publik dan `/login` tetap ○.
- Sidebar dan bar atas menampilkan user yang login; bagian Editor dan badge antrean review hanya untuk admin. `getPreviewUser` dihapus.

**E2E:**

- Project `setup` (`e2e/auth.setup.ts`) login sekali sebagai admin dan sekali sebagai author, lalu menyimpan sesinya di `e2e/.auth/` (git-ignored). Semua project memakai sesi admin; test lain memakai `AUTHOR_STATE` atau `NO_SESSION` dari `e2e/auth.ts`.
- `e2e/access.spec.ts` dan `e2e/flows.spec.ts` menguji login (benar, salah, akun nonaktif, tanpa JavaScript, cookie `httpOnly`/`Lax`), tamu dan cookie palsu → `/login`, author di setiap halaman admin → `/dashboard`, artikel orang lain tidak ditemukan, dan logout.

**Untuk Fase 4 dan 5:**

- **Akun dinonaktifkan atau password diganti saat cookie masih sah:** proxy meloloskannya, lalu halaman mengalihkan lewat pengalihan yang butuh JavaScript (200 + `NEXT_REDIRECT`). Tanpa JavaScript, pengunjung hanya melihat halaman kosong; datanya tidak terkirim.
- **`?next=`** belum ada. Kalau ditambahkan, hanya terima path yang diawali `/` dan bukan `//` atau `/\`.
- **Sudah login lalu membuka `/login`:** form tetap tampil.
- **Redirect setelah login dan logout** tidak memakai fade halaman, karena transisi Server Action tidak bertipe `page`.
- **Index `lower(email)`:** belum ada; tambahkan lewat migration baru bersama unique index saat fitur kelola penulis (Fase 4).
- **Setiap Server Action di Fase 4** memanggil `getCurrentUser()`/`requireUser()` sendiri.
- **Rate limit login** (Fase 5). Di belakang reverse proxy, isi `serverActions.allowedOrigins`.
- **`next start` lewat http ke IP LAN** tidak bisa login, karena cookie-nya `secure`. Coba di HP dengan `next dev`, atau lewat https.
